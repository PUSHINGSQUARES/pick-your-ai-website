## Authority and lifecycle model

### Current guest-local branch

A local draft ID identifies an app-private record. Its revision/hash token controls which acknowledged state may be changed; neither value authenticates a person. The application may create, list, rename through an edit, duplicate, open or explicitly delete its local records according to the canonical library's storage checks.

Pending form content is not automatically a saved revision. A conflict, uncertain write, unavailable selection or corrupt record must not grant a fresher save token. Explicit deletion names the affected local ID and retained history. Other local drafts remain outside that deletion's scope.

The diagnostic keeps data in app-private storage with backup disabled at the pinned source. That does not prove secure erasure from flash, retrieval from an operating-system backup, or deletion of an exported copy. A completed local removal says only that the selected local files were removed under the supported storage protocol. Interrupted cleanup remains identifiable and retryable; it is not reported as confirmed remote deletion.

### Requirements before any remote guest or account branch

The server must derive the actor or scoped capability from a verified session/capability, not from a supplied owner_ref, local UUID, revision token or claimed email. Private reads and writes require object-level authorization. Share links need explicit scope, expiry/revocation semantics and a safe projection; possessing a link must not grant unrelated mutation authority.

Retries require the accepted idempotency and conditional-update behavior. An ambiguous response must be reconciled without duplicating a server mutation. Local deletion, a remote deletion request and a server-confirmed deletion are separate states. A queue must retain its actor/scope and cannot replay under a new identity merely because the device has a different login.

An account upgrade would explain which local records and fields will leave the device, which service receives them and how retention/deletion works. Consent to sign in is not consent to upload every local record. The client must bind the returned server identity/version explicitly, preserve conflicts and incomplete input, and avoid presenting an unconfirmed transfer as synchronized.

Sign-out or account switching would revoke/cancel applicable sessions and in-flight work, partition or remove private cache according to the accepted policy, and prevent prior-account requests from entering the new account's state. Unsynchronized-data consequences must be shown before a destructive action. No such account flow is enabled by this decision; the requirements are retained for #42/#62/#63/#78/#95/#105/#123/#125 and research #42.
